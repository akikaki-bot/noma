> **ステータス:** 設計中 / v0.0.1（2026-10-15時点の会話を整理）  
> **目的:** Codexなど、元の会話を参照できない実装担当者へ、決定事項・設計意図・未決定事項を引き継ぐ。

## 0. まず読んでほしい設計思想

この言語は、**高水準・汎用・静的型付け**を志向する。ユーザーは「言語を設計すること」を主に楽しみたい。メモリ管理やポインタ操作を利用者に要求したくない。一方で、型、値の変更権限、外部から見える名前、エラー経路については**ソース上で意図が明示されること**を好む。

核心となる原則は次のとおり。

1. **型は宣言時に明示する。** ローカル変数の型推論は行わない。ただし型検査器が式の型を計算し、型の絞り込みを行うのは当然必要。
2. **変更は明示する。** 不変（Deep Readonly）がデフォルト。変更可能な変数・関数引数・変更権限の引き渡しは `mut` で示す。
3. **予期しない変更の伝播を防ぐ。** 可変な値を独立した不変値として保持する場合は `snapshot` を明示する。
4. **名前の由来を明確にする。** モジュールの読み込みには `use "package/path" as alias;` を要求し、暗黙のグローバル展開をしない。
5. **言語本体は小さく保つ。** I/O は組み込み `print` ではなく標準ライブラリから呼び出す。最終的には標準ライブラリの大部分を自作言語で記述する。
6. **制御フローを静的に保証する。** エラー処理と `match` は値と型を持つ構文として設計する。
7. **将来のセルフホスティングを視野に入れる。** ただし初期段階からネイティブコード生成・JIT・GC実装を要求しない。

## 2. 変数宣言・不変性・`mut`

基本的な想定構文:

```text
let original: int32 = 10;
let mut editable: int32 = 10;

original = 20; // コンパイルエラー: 不変
editable = 20; // OK
```

- 修飾子なしの束縛は**読み取り専用**。再代入だけでなく、ネストしたフィールド・配列要素の変更も不可（Deep Readonly）。
- `mut` の束縛は**読み書き可能**。対象の内部にも、許される範囲の変更権限が伝播する。
- 可変値の**通常の読み取りはOK**。例えば `io.write(...)` で現在値を表示する読み取りや、readonly引数へ渡してその場で参照する用途は許す方向。
- ただし、可変値を**別の不変束縛として保持**する場合、暗黙の共有・コピーを許さず、`snapshot` を要求する。
- これは単なるRustの `mut` の模倣ではない。**「知らない間に他所で変更された値を参照してしまう」ことを防ぐ**のが第一目的。

```text
let mut counter: int32 = 10;
counter = 20;

let a: int32 = counter;          // コンパイルエラー
let b: int32 = snapshot counter; // OK: b は20で独立

counter = 30;
// b は20のまま
```

### 2.1 Deep Readonly

```text
type User = struct {
    name: string;
    scores: Array<int32>;
};

let user: User = ...;
user.name = "Bob";       // エラー
user.scores[0] = 100;    // エラー

let mut editable: User = ...;
editable.name = "Bob";   // OK（別の安全制約を満たす場合）
editable.scores[0] = 100; // OK
```

`readonly` は変数名への再代入禁止にとどまらず、アクセス先の値にも伝播する。値の内部に可変オブジェクトへの別名が潜むことでこの保証が破られないよう、ランタイムの値表現・代入・ネイティブ境界も含めて検討する。

### 2.2 `snapshot`

` snapshot expr ` は、**その時点の値を元の変更可能な状態から独立させて取り出す**式。結果はreadonlyな値として扱う。新しい `let mut` の初期値として利用して、独立した変更可能値を作る用途も想定している。ただし詳細な型付け規則は今後形式化する。

```text
let mut array: Array<string> = ["Alice", "Bob"];

let a: string = array[0];          // コンパイルエラー: 可変由来の値を保持
let b: string = snapshot array[0]; // OK: 要素の独立値

array[0] = "Charlie";
// b は "Alice" のまま
```

`snapshot array[0]` は要素のみを独立させ、`(snapshot array)[0]` は配列全体を独立させるという意図がある。演算子の結合優先順位と「要素自体が参照型の場合、どこまで独立させるか」は今後明文化する。

実装戦略はディープコピーでも Copy-on-Write でもよいが、**外から観測した結果の独立性**を保証すること。単なる浅い参照コピーでは不可。

## 3. 関数の引数と変更権限

通常引数はreadonly。可変な引数を受けるには、**宣言側と呼び出し側の両方で** `mut` を明示する。

```text
fn increment(mut value: int32) -> void {
    value++;
}

fn show(value: int32) -> void {
    // value を読み取れるが変更不可
}

fn main() -> int32 {
    let mut count: int32 = 10;

    show(count);          // OK: readonlyとして読み取り
    increment(count);     // コンパイルエラー: 呼出側の変更許可がない
    increment(count); // OK: count が11になる

    let saved: int32 = snapshot count;
    return 0;
}
```

`mut` 引数に対する変更は**呼び出し元の値に反映される**。一方、通常のreadonly引数は呼び出し元が `mut` であっても変更権限を得ない。

**未決定（重要）:** 同じ値に対する複数の `mut` アクセスの競合、readonly参照と `mut` 参照の同時存在、クロージャ・非同期処理への捕捉、参照の関数外への脱出、引数が値なのか借用ビューなのか。実装時に安全性を犠牲にして仮決定しないこと。

## 4. 型構築、構造的型付け、部分型付け

### 4.1 型構築と型の命名の分離

C言語の `typedef` に関心はあったが、最終的な方向は「**型を作る式**と、**その型に名前を付ける宣言**を分離する」こと。

```text
type User = struct {
    name: string;
    age: int32;
};

type Identifier = int32 | string;
type AnotherIdentifier = Identifier;
```

上記の `type = struct` 構文は現状の最有力案であり、Cの `struct User` タグ名前空間をそのまま導入することは**決まっていない**。

### 4.2 構造的型付け

```text
type A = struct { value: int32; };
type B = struct { value: int32; };
// A と B は構造が同一なので同じ型として扱う
```

異なる名前でも構造が同一なら同じ型として扱う。コンパイラ内部で構造的な型をinterningする最適化は可能だが、これ自体が実行速度の向上を保証するわけではない。

### 4.3 幅の部分型付け

```text
type A = struct { x: int32; };
type B = struct { x: int32; y: int32; };

let b: B = B { x: 10, y: 20 };
let a: A = b; // OK（bが不変であることにも注意）
```

`B` は `A` の要求フィールドをすべて持つので `B <: A`。逆方向は認めない。ただし**可変な構造体やフィールドを介して部分型付けが型安全性を破らない規則**は未決定。可変参照の共変性を安易に許可しないこと。

### 4.4 Union型

`A | B` を表す型式を導入する。同じ構成要素のUnionは順序に依存せず同一視する方向。

```text
type Value = string | int32 | bool;
type Other = bool | string | int32; // Valueと同等の型として扱う方向
```

Unionの正規化、重複除去、包含関係、実行時型タグ、`throwable` と正常型が構造的に重なる場合の判別方法はこれから形式化する。

## 5. `match`：式と文の両用

`match` は**値を返す式**として採用し、結果を破棄すれば文としても使えるようにする。静的にUnion型の分岐と網羅性を検査する。

```text
type Value = string | int32 | bool;

fn classify(value: Value) -> int32 {
    return match (value) {
        case (v: string) { 1 }
        case (v: int32)  { 2 }
        case (v: bool)   { 3 }
    };
}

let result: int32 = match (someValue) {
    case (v: string) { 10 }
    case (v: int32)  { 20 }
    case (v: bool)   { 30 }
};
```

- `case (v: T)` の分岐内で `v` を `T` として扱う。
- Union型のすべての可能性を網羅していない場合は、値を破棄する文として使ったときもコンパイルエラーにする方向。
- `match` 全体の型は、各分岐が生成する型を検査して求める。これは**変数の型推論**とは別の「式の型計算」。
- `let result: string = match (...) { ... }` と宣言して `int32` の経路が残るならコンパイルエラー。
- 分岐末尾の式がそのブロックの値になる構文を想定している（正式なブロック式文法は未決定）。
- 構造的型付けで複数ケースに同時に該当する可能性、優先順位、ネスト・リテラルパターンの範囲は未決定。

## 6. `T | throwable` と後置エラーハンドラ

エラーは通常の返り値の型（例 `T | throwable`）として扱い、後置ハンドラで成功値 `T` に絞り込む。`throwable` を通常の例外送出機構と同一視するかどうかはまだ未決定。

### 6.1 `catch e { ... }` — エラー経路から脱出

```text
let value: int32 = io.readInt()
    catch e {
        io.puts(e.toString());
        return -1;
    };
// ここに到達するなら value は int32
```

- エラー経路のハンドラは**正常完了できない**必要がある。`return`、将来の例外送出・終了命令などで脱出し、その経路の型は `never`。
- 概念的には `T | never` が `T` に簡約される。
- 単にメッセージを表示してブロック末尾に到達するコードはコンパイルエラー。

### 6.2 `otherwise e { ... }` — 代替値を生成

```text
let value: int32 = io.readInt()
    otherwise e {
        io.puts("Invalid input");
        0
    };
// エラー時は0、それ以外はreadInt()の成功値
```

- 成功側の型 `T` と互換な代替値を生成し、続行できる。
- `otherwise` 内に関数から `return` する経路が混ざることは許容する方向（`never` は継続値を要求しない）。
- `void`（正常に完了するが値を持たない）と `never`（その地点から正常継続しない）を区別する。
- `break` にハンドラ固有の「関数からreturnする」意味は持たせない。通常のループ脱出のみ。`continue` の通常規則以外の特例も未採用。

### 6.3 エラー機構の未決定事項

- `throwable` の内部表現・継承/構造・ユーザー定義・エラー判定方法。
- Union型の構造的重なりをどう安全に判別するか。
- `catch e {}` が本物の例外送出と混同されるのをどう扱うか。
- `otherwise` のブロック式文法、例外伝播、関数の戻り値規則。

## 7. モジュール・名前空間・可視性

読み込み構文は**確定**:

```text
use "std/io" as io;
use "std/math" as math;

io.puts("Hello"); // OK（関数が公開されている場合）
puts("Hello");    // コンパイルエラー: 暗黙のグローバル展開はしない
```

- `as` とエイリアス識別子は必須。
- `use "std/io";` は不可。
- `alias.member` 形式で公開メンバーにアクセスする。
- `pub` を付けた宣言のみ外部公開。付けなければ非公開。
- `private` / `priv` は導入しない。

```text
pub fn hello() -> void { /* 外部へ公開 */ }
fn internal() -> void { /* モジュール内部のみ */ }
```

クラスを将来導入する場合のメンバー単位の公開範囲や、同一モジュール・同一ファイル・クラス内での非公開の境界は未決定。

## 8. 標準ライブラリとNative Bridge（Stage 1）

### 8.1 役割分担

```text
ユーザーコード
  use "std/io" as io;
       ↓
自作言語で記述した標準ライブラリ（std/io 等）
       ↓
信頼されたnative fnの呼び出し
       ↓
TypeScript製 Native Registry / ランタイム
       ↓
Node.js / OS
```

I/O を言語組み込み `print` にしない。基本型・最低限の演算はコンパイラの責務とし、I/O、文字列ユーティリティ、ファイル、数学などの機能は徐々に標準ライブラリへ移す。

標準I/Oモジュールの現在の名前は **`std/io`**。途中の会話で出てきた `std/stdio` は旧例であり、今後の実装では `std/io` を優先する。

### 8.2 `native fn` と `TSAny`

会話で採用した方向性:

```text
compilerOnly type TSAny = /* Native Bridge */;

native fn write(args: TSAny) -> void;
```

これは**native関数への境界を表現するための例示的な宣言**。`compilerOnly` の厳密な文法、`TSAny` の割当可能性、`native` 関数の名前解決はStage 1で仕様化する。

- `compilerOnly` は一般ユーザーが任意に新しい特権型を作る手段にはしない。
- `TSAny` はTypeScriptホスト境界専用の特殊型であり、一般ユーザーコードの型検査回避に使わせない。
- `native fn` は信頼された標準ライブラリ・ランタイムなどに限定する。
- TypeScript側には型付きの Native Registry を設け、モジュール名と関数名で実体を対応づける。
- `TSAny` をTypeScriptの野放図な `any` と同じにしない。境界での入力検証と通常型への安全な復帰を行う。
- 最初の `write` は最低限の例であり、最終API名称・引数・戻り値は未決定。

将来の標準ライブラリ側の例（**仮構文**）:

```text
// std/io モジュール側のイメージ
native fn write(value: TSAny) -> void;

pub fn puts(value: string) -> void {
    write(value + "\n");
}
```

**注意:** `native fn write(value: TSAny)` に通常の `string` を安全に渡すための変換・境界規則はまだ決まっていない。例をそのまま無検査で実装してはならない。

### 8.3 `std/io` にまず欲しい機能（実装候補・まだ正式APIではない）

- 標準出力への `write` と改行付き `puts`。
- 標準エラー出力への出力。
- 標準入力からの `readLine`。
- UTF-8を基本とした文字列入出力。
- EOFの区別、入力失敗とOS側エラーの区別。
- 失敗するI/Oと `T | throwable`・`throw` / `otherwise` との接続。

`printf` / `scanf` は書式指定と型の整合性が難しいため初期必須機能としない。`std/io` の具体的な公開関数群は、設計・テストを通して確定させる。

## 9. 開発計画

### Stage 0 — 基本処理系

TypeScript / Node.js でLexer、Parser、AST、名前解決、型検査、最小インタプリタ、診断出力、テストを実装する。言語仕様の実験と変更のしやすさを優先する。

最初の縦切りは、型注釈必須の変数宣言・算術・比較・関数宣言と呼び出し・`return`・基本的な `mut` / `snapshot` の検証を推奨。未実装構文はエラーとして報告する。言語仕様を全て一度に実装しない。

### Stage 1 — 自作言語製stdlibとnative bridge

`compilerOnly` / `TSAny` の特権境界、`native fn`、TypeScript Native Registry、`use "std/io" as io;` のロード機構を実装する。`std/io` を自作言語で書き、ホスト依存部分だけTypeScriptに委譲する。標準入出力とEOF・失敗系のテストを用意する。 **ただしStage 1の最初に `T | throwable` が未実装なら、まず成功する基本出力の縦切りを完成させる。EOFやエラーを含む入力APIは、それを安全に表す型機構が整うまで正式公開せず、テスト用の仮APIとも明確に区別する。**

### Stage 2以降 — 言語機能の拡張とセルフホスティング

Union型・構造的型付け・幅の部分型付け・`match`・`throw` / `otherwise` などを安全に完成させる。必要ならBytecode VMやコンパイル方式へ移行し、ゆくゆくは自作言語でコンパイラ/stdlibの主要部を書き直す。**具体的な順番・年次・自己コンパイルの条件は未確定**。

## 10. 実装時に守ること

- **決定事項と提案を明確に分離**する。未確定事項は設計メモとして記録し、実装しやすいだけの理由で恒久仕様にしない。
- 既存のリポジトリやコードがあれば、先に調べて現状とこの仕様の差分を明示する。
- 型検査、可変性、安全性はランタイムの偶然の挙動に任せず、静的に可能な限り検査する。
- 参照共有でDeep Readonlyやsnapshotの独立性が破れる実装は不可。
- 正常系だけでなく**コンパイルに失敗すべきサンプル**をテストに含める。
- Lexer/Parser/型検査/実行器と、診断メッセージ（ソース位置・期待型・実際の型）を分離する。
- TypeScript実装側でも `any` の濫用を避ける。ただしホスト境界が必要な場合は `unknown` と検証ロジックを用いる。
- `std/io` は一般ユーザーに `TSAny` を露出しない公開APIを設計する。
- 「完成しました」と言う前に、CLIによる実行とテストで確認する。
